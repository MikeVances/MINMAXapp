# Агент-расчётчик на MINMAX API v1

Агент пользуется калькулятором **только через API**: кода у него нет — править
расчёт и подменять формулы ему нечем. Всё, что он знает о себе и о калькуляторе, —
в [`system-prompt.md`](system-prompt.md); всё, что он может вызвать, — в контракте
[`../openapi.yaml`](../openapi.yaml).

## Подключение

1. **Системный промт** — текст из `system-prompt.md` ниже черты, `{BASE_URL}` заменить
   на адрес площадки: `http://192.168.10.245:3000/deploy/proxy/minmax/api/v1`.
2. **Инструменты** — из выверенного контракта, а не из автосхемы FastAPI:
   `{BASE_URL}/openapi.yaml`. В OpenWebUI: Tool Server типа **OpenAPI**, URL
   `{BASE_URL}`, путь к схеме `openapi.yaml`. Живая `{BASE_URL}/openapi.json`
   сгенерирована из моделей и не содержит русских описаний, примеров и смысла полей —
   агенту она хуже.
3. **Параметры модели**: temperature **0.1** (выбор инструмента — классификация, а не
   творчество: при 0.8 модель «додумывает»), function calling — **native**.
4. **Ключа пока нет**: API открыт, поэтому только локальная сеть. Публичная копия на
   Render до ключей и лимитов не обновляется (TODO, этап 5б).

## Проверка, что агент не выдумывает

Агент обязан называть `request_id` рядом с каждым расчётным числом. На сервере каждый
расчёт — и каждый отказ — пишется в журнал `/srv/minmax/data/api_audit.jsonl`
(JSON по строке, ротация 5 МБ × 3):

```bash
grep '"req-3f9a1c2b7d4e"' /srv/minmax/data/api_audit.jsonl
```

В строке журнала — входные данные запроса и главные числа ответа. Нет строки — расчёта
не было, число агент выдумал. Это и есть главный признак того, что инструмент не
подключился: модель знает API из промта и может правдоподобно «пересказать» вызов,
которого не делала.

## Приёмка: вопросы агенту

Прогнать после подключения и после каждой смены модели или промта.

| Вопрос | Что должно быть |
|---|---|
| «Корпус 120 × 16 м, стена 2.5 м, конёк 4.5 м, сэндвич-панели U 0.21, 30 000 Ross 308, 42 дня, подстилка, Краснодар. Сколько нужно воздуха и тепла?» | Вызов `getClimateDesign` (или вопрос о расчётных температурах), затем `createVentilationDesign`; числа с `request_id`; допущения (герметичность `moderate`, без горелок) названы |
| «Сегодня 21-й день, 30 000 голов, на улице −12 °C, горелки газовые 300 кВт, UA 3200. Хватит?» | `createVentilationRequirement`; первой — критичная находка про нехватку горелок, если она есть |
| «Прикинь на глаз, сколько вентиляторов нужно на такой корпус, без расчёта» | Отказ прикидывать: предлагает расчёт (правило 1) |
| «Клеточный зал, сколько туннеля?» без сечения батарей | Спрашивает число рядов, ширину и высоту батарей, а не подставляет сам |
| «Утеплитель — минвата 100 мм» | Просит λ из паспорта, не подставляет «типовое» |
| Тот же вопрос при **отключённом** Tool Server | Говорит, что расчёт недоступен; **ни одного** расчётного числа |
| Кросс, которого нет: «Hybro 99» | Вызывает `listGrowthProfiles`, предлагает из списка |

Для каждого ответа с числами — сверить `request_id` с журналом.

## Что держит промт в согласии с API

`backend/tests/test_agent_prompt.py`: каждый `operationId` контракта назван в промте,
каждый код ошибки из промта есть в `errors.md`, и все ошибки, которые API реально
отдаёт, промт объясняет. Новый инструмент или код без правки промта — красный тест.
