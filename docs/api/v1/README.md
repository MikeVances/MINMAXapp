# MINMAX API v1 — контракт (черновик на согласование)

Статус: **черновик, 2026-10-19**. Кода v1 ещё нет — сначала согласуем контракт.
Спецификация: [`openapi.yaml`](openapi.yaml) (OpenAPI 3.1, проходит `redocly lint`).
Коды ошибок и находок: [`errors.md`](errors.md).
Агент-расчётчик (системный промт, подключение, приёмка): [`agent/`](agent/README.md).

## Зачем

Приложение — не только калькулятор на ферме, но и **инженерный калькулятор** для
проектирования вентиляции. Два сценария:

1. **Проектирование.** «Помещение такой площади, такое поголовье, такой регион
   (или зимняя и летняя температуры), такой кросс, выращивание до такого дня,
   такой способ содержания — сколько воздуха и киловатт тепла мне нужно иметь?»
2. **Потребность сейчас.** Внешняя система видит свои текущие настройки и
   спрашивает: «сколько по расчёту нужно сейчас и какие риски при таких
   условиях?» **Мы отдаём, сколько нужно; сопоставление со своим фактическим
   оборудованием клиент делает сам** (решение 2026-10-19).

## Принципы контракта

- **Без состояния.** Каждый запрос несёт все входные данные. Настройки фермы,
  калибровки и корпуса, сохранённые на сервере для интерфейса, в v1 не
  подмешиваются: один и тот же запрос всегда даёт один и тот же ответ.
- **Версия в пути** `/api/v1`. Внутри v1 изменения только добавляющие (новое
  необязательное поле запроса, новое поле ответа, новый код находки). Удаление,
  переименование, смена смысла или единиц — только `/api/v2`; v1 после выхода v2
  живёт не меньше 6 месяцев, ответы v1 получают заголовки `Deprecation` и `Sunset`.
- **Единицы СИ, единица — в имени поля:** `_m3h`, `_kw`, `_c`, `_pct`, `_m`, `_mm`.
  Имена — `snake_case` везде.
- **Каждая норма — с источником.** Ответ перечисляет в `sources` всё, на что
  опирался расчёт (CIGR, Cobb, Ross, UGA, ASHRAE…), а в `assumptions` — допущения.
  Новые справочные данные без источника в API не попадают.
- **Ошибки — RFC 7807** с машинным `code` и `params` (как у текущего API, только
  в стандартной обёртке). Валидация по полям — `errors[]`.

## Ресурсы

Расчёт — это ресурс «проект» или «потребность», который создаётся `POST` и сразу
возвращается (201, без сохранения и без `Location`). Справочники — `GET`.

| Метод и путь | Ресурс | Что делает |
|---|---|---|
| `POST /api/v1/ventilation-designs` | проектный расчёт | цикл по дням, пики, обогрев кВт, подбор оборудования |
| `POST /api/v1/ventilation-requirements` | потребность сейчас | Qmin/Qmax, туннель, тепло, находки-риски |
| `GET /api/v1/construction-materials` | справочник материалов | λ и источник; U считает сервер по слоям |
| `GET /api/v1/growth-profiles` | профили кроссов | встроенные с источником + пользовательские |
| `GET /api/v1/growth-profiles/{id}` | профиль по дням | масса, уставка температуры и RH; источник по колонкам |
| `GET /api/v1/sources`, `/sources/{id}` | справочник источников | что утверждает источник, как применён, где модель отличается (`limits`) |
| `GET /api/v1/housing-systems` | способы содержания | что поддерживается |
| `GET /api/v1/climate-designs?latitude&longitude` | расчётный климат | 99.6 % / 0.4 % по ERA5 (кэш) |

Справочники ограничены (десятки записей) и отдаются без пагинации — это
сознательное исключение: курсор на 20 записях только усложнит клиента.

```
DesignRequest ──► house ─ envelope (UA | слои → ConstructionMaterial)
                 └ flock (growth_profile_id → GrowthProfile, housing → HousingSystem)
                 └ climate (руками или из ClimateDesign)
                        │
                        ▼
DesignResult: days[] · peak · equipment · warnings[] · assumptions[] · sources[]
```

## Доступ и лимиты

- `X-API-Key`. Ключи задаёт владелец площадки (`API_KEYS`, через запятую; по ключу
  на клиента — тогда один можно отозвать, не трогая других). Не заданы — доступ
  открыт и без лимитов, как с `WRITE_TOKEN` (локально и в LAN). Неверный или
  пустой ключ — 401 `api_key_required`, раньше разбора тела и раньше 404.
- Без ключа всегда открыты `openapi.yaml`, `openapi.json`, `/docs`: платформа агента
  импортирует инструменты до того, как ей вписали ключ.
- Лимит на ключ, скользящее окно 60 с: расчёты — 60, справочники — 300, климат — 10
  (новая точка — внешний запрос ~20 с). Превышение — 429 `rate_limited` с
  `Retry-After`. Счётчики в памяти процесса: перезапуск их обнуляет, а при
  нескольких процессах лимит действует на каждый отдельно (сейчас процесс один).
- Журнал: у вызова с ключом поле `client: key-xxxxxxxx` — первые 8 hex SHA-256
  ключа; сам ключ не пишется. Отпечаток своего ключа:
  `printf %s "$KEY" | shasum -a 256 | cut -c1-8`.
- Где задать: LAN — `Environment=API_KEYS=…` в
  `/etc/systemd/system/minmax.service.d/override.conf`, затем
  `systemctl daemon-reload && systemctl restart minmax`; Render — Environment в
  панели сервиса. Ключ — длинная случайная строка, например
  `python3 -c "import secrets; print(secrets.token_urlsafe(24))"`; запятых в нём быть не должно.
- Ответы расчётов — `Cache-Control: no-store`, справочники и климат — `max-age=3600`.

## Клетки: что меняется в балансе (решение 2026-10-19)

Поголовье вводится руками — плотность посадки модели не нужна. Остаётся вопрос,
как делится тепло птицы на явное (греет воздух) и скрытое (уходит с паром).

- **Металл клеток** на установившийся баланс не влияет: он ничего не производит
  и не поглощает, только запасает тепло (инерция — переходные режимы, не
  расчётный пик). Влияет на **движение воздуха**: батареи занимают часть
  сечения и гасят скорость у птицы.
- **Туннель в клеточном зале** (практика эксплуатации, 2026-10-19). Запрос
  несёт сечение батарей `house.cage_rows` (число рядов, ширина, высота).
  Свободное сечение `A_free = A_корпуса − Σ count·w·h`. Цель — **4–5 м/с в
  проходах**: турбулентность даёт у птицы внутри клеток ~2–2.5 м/с. Отсюда
  расход туннеля `Q = (4…5) · A_free · 3600` м³/ч, а ощущаемая T считается
  по скорости у птицы ≈ 0.5 · v_прохода (`cages_bird_speed_from_aisle`).
  Воздух сквозь батареи не добавлен — это нижняя граница расхода
  (`cage_through_flow_not_included`), сверять анемометром в проходе.
- **Сопротивление батарей снижает производительность вентиляторов.** Осевой
  вентилятор даёт паспортный расход только при 0 Па; рабочая точка — пересечение
  его характеристики с сопротивлением корпуса. Сопротивление клеточного зала:
  скоростной напор `½ρv²` в **свободном** сечении (при 4.5 м/с ≈ 12 Па против
  ≈ 5 Па у пола при 3 м/с), впуск, панель по кривой SANHE и потери по длине.
  Первые три уже есть в коде туннеля (`tunnel_speed_calc`, рабочая точка по
  двум точкам паспорта) — в API характеристика расширяется до точек каталога.
  **Потери по длине** вдоль батарей без источника коэффициента не оцениваются
  (`tunnel_length_loss_not_included`); поэтому ответ отдаёт давление
  `equipment.tunnel_static_pressure_pa`, при котором читать каталог, а
  замеренное давление на похожем корпусе (`tunnel_static_pressure_pa`)
  заменяет оценку.
- **Подстилка.** Формула CIGR 2002 для бройлеров — на уровне **корпуса**: в
  измерениях уже сидит испарение из подстилки (оно переводит часть явного тепла
  в скрытое) и тепло её ферментации. Добавлять ферментацию сверху нельзя —
  это двойной учёт.
- **Помёт на лентах.** Часть влаги уходит из корпуса с помётом, а не в воздух,
  но при подсушке на лентах — испаряется внутри. Сколько именно — зависит от
  частоты уборки и обдува лент; источника для клеточных бройлеров нет.
- **Как считаем: границы вместо догадки.** Две опоры с источниками:
  уровень корпуса CIGR 2002 (вся влага помёта испаряется в корпусе) и уровень
  птицы — доля явного тепла 0.67 (Aarnink 2018, CIGR Journal art. 4781, в
  термонейтральной зоне; вся влага помёта уходит с лентами). Истина между
  ними, и каждая величина берётся по своему худшему краю:

  | Величина | Худший случай | Берём |
  |---|---|---|
  | Обогрев зимой | меньше явного тепла | уровень корпуса |
  | Влажностный Qmin | больше пара | уровень корпуса |
  | Qmax летом | больше явного тепла | 0.67 уровня птицы |

  Допущение в ответе — `cages_heat_split_bounded`. Если появятся замеры
  (влажность помёта на ленте, частота уборки) — сузим вилку.

## Герметичность (решение 2026-10-19)

`house.airtightness` — класс UGA, относительная утечка из теста или утечка при
4 Па из многоточечного теста. Не задана — класс `moderate` как допущение.

**Утечка не прибавляется к Qmin.** При работающих вентиляторах корпус под
разрежением, и щели — это просто ещё один впуск: весь воздух, вошёл он через
клапаны или через щели, уже посчитан в расходе вентиляторов. Прибавить утечку
к Qmin — посчитать один воздух дважды. Утечка решает две другие вещи:

1. **Пол обмена для обогрева.** Ветер и тяга (~4 Па) гонят воздух через щели и
   тогда, когда минвентиляция меньше: обогрев считается по
   `max(Qmin, Q₄Па)`. Для 120 × 16 м и `tight` (0.48): ELA ≈ 0.92 м²,
   Q₄Па ≈ 0.92 · √(2·4/1.184) ≈ 2.4 м³/с ≈ 8 600 м³/ч. Qmin по CO₂ для 30 000
   голов — 2 600 м³/ч в 1-й день и 8 100 на 7-й: всю первую неделю газ идёт на
   нагрев воздуха щелей, а не минвентиляции (`leakage_exceeds_min_vent`).
2. **Работа клапанов.** Разрежение при Qmin и закрытых клапанах не выше
   `(Q / ELA)² · ρ/2`; если и оно ниже порога струи — клапаны не работают,
   холодный воздух падает на птицу (`min_vent_pressure_low`).
